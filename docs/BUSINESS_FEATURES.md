# Case Viewer — Business Features

_Last reviewed: 2026-09-24 (based on the current `master` working tree)_

## 1. Purpose

Case Viewer is a back-end service for **case management**. A case is a unit of work, such as a customer service
investigation. Each case has a timeline of **activities** that record what was done, by whom, and when.

The service lets authenticated users:

- register and log in,
- create cases,
- look up a case, including its activity history, by its business case number,
- list all cases.

It is a REST API only. There is no user interface; clients call it directly (Swagger UI, Postman, or another front end).

Base URL: `http://<host>:8081/case-viewer`

## 2. Business domain

### 2.1 Case

| Field         | Business meaning                                   | Rules                                  |
|---------------|----------------------------------------------------|----------------------------------------|
| `caseId`      | System identifier (UUID)                           | Generated by the system                |
| `caseNumber`  | Business reference, e.g. `CASE-100001`             | Required, **unique**, max 30 chars     |
| `title`       | Short summary of the case                          | Required, max 200 chars                |
| `description` | Details of the request or issue                    | Optional, max 2000 chars               |
| `status`      | Where the case is in its lifecycle                 | Required, one of the statuses below    |
| `createdAt`   | When the case was opened                           | Set by the system                      |
| `updatedAt`   | When the case last changed                         | Set by the system                      |
| `activities`  | Activity timeline, oldest first                    | Returned when a case is viewed         |

The system also keeps a hidden `version` number for optimistic locking, so two concurrent updates to the same case
cannot silently overwrite each other.

**Case statuses**

```
OPEN ──► IN_PROGRESS ──► RESOLVED ──► CLOSED
```

| Status        | Meaning                                  |
|---------------|------------------------------------------|
| `OPEN`        | Case raised and not yet picked up        |
| `IN_PROGRESS` | Someone is working on the case           |
| `RESOLVED`    | The issue is addressed; awaiting closure |
| `CLOSED`      | Case is finished                         |

> The arrow shows the intended lifecycle. The system does **not** enforce transitions yet: any status can be set when a case is created.

### 2.2 Activity

An activity is one step in a case's history, such as "case created" or "documents reviewed".

| Field          | Business meaning                                   | Rules                         |
|----------------|----------------------------------------------------|-------------------------------|
| `activityId`   | System identifier (UUID)                           | Generated by the system       |
| `activityType` | Kind of step, e.g. `CASE_CREATED`, `DOCUMENT_REVIEW` | Required, free text, max 100 |
| `description`  | What happened                                      | Required, max 2000 chars      |
| `status`       | State of this step                                 | Required, see below           |
| `performedBy`  | User or system that did it, e.g. `agent01`, `system` | Optional, max 100 chars     |
| `activityAt`   | When it happened                                   | Required                      |

**Activity statuses:** `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`.

**Relationship:** one case has many activities. Activities belong to exactly one case and are deleted along with it.
When a case is viewed, its activities are listed in chronological order.

### 2.3 User

| Field      | Rules                                              |
|------------|----------------------------------------------------|
| `username` | Required, unique, at least 3 characters            |
| `password` | Required, at least 8 characters, stored hashed     |
| `role`     | Every self-registered user gets `USER`             |
| `enabled`  | Disabled users cannot log in                       |

## 3. Features

### F1. User registration

A new user creates an account with a username and password.

- `POST /api/auth/register` (public)
- Rejects a username that already exists (`400 INVALID_ARGUMENT`, "Username already exists").
- Rejects a username shorter than 3 characters or a password shorter than 8 (`400 VALIDATION_ERROR`).
- New users receive the `USER` role and are enabled right away.
- Returns the new user's id, username and role. The password is never returned.

### F2. User login

A registered user exchanges their username and password for an access token.

- `POST /api/auth/login` (public)
- Returns a JWT bearer token, valid for **1 hour** in dev (`jwt.expiration=3600000`).
- The client sends the token with each later request: `Authorization: Bearer <token>`.
- The session is stateless. Once the token expires, the user must log in again. There is no refresh or logout.

### F3. View a case with its activity history (primary feature)

A user looks up a case by its case number and sees the case details and its full activity timeline.

- `GET /api/cases/{caseNumber}` (authenticated)
- Returns the case fields plus `activities[]`, oldest first.
- Unknown case number → `404`, with error code `ORDER_NOT_FOUND`.
- An optional `tenant-id` header is accepted but **not used** yet (see §5).

Example: `GET /api/cases/CASE-100001` returns the "Customer service case" with two activities, `CASE_CREATED` and
`DOCUMENT_REVIEW`.

### F4. Create a case

A user opens a new case.

- `POST /api/cases/create` (authenticated)
- Body: `caseNumber`, `title`, `description`, `status`.
- Returns the created case with an empty activity list.
- The system does not add a `CASE_CREATED` activity automatically.

```json
{
  "caseNumber": "CASE-100010",
  "title": "Refund request",
  "description": "Customer disputes a duplicate charge.",
  "status": "OPEN"
}
```

### F5. Case summary lookup (lightweight)

Returns a case's core fields without its activities. This is a cheaper read for list or summary screens.

- `GET /api/cases/search/{caseNumber}` (authenticated)
- `activities` is always an empty list.
- Every call is audited: start, end and duration are logged.
- Unknown case number → `200` with an empty body, **not** `404` (see §5).

### F6. List all cases

Returns every case, for reporting or back-office screens.

- `GET /api/cases/search/jdbc/all` (authenticated)
- Uses the Oracle stored procedure `GET_ALL_CASES`.
- There is no paging or filtering. Every case is returned in one response.

### F7. Direct case lookup (JDBC) — prototype

- `GET /api/cases/jdbc/{caseNumber}` (authenticated)
- **Not usable as a business feature.** It ignores the path variable and always returns `CASE-100002`.

## 4. Cross-cutting capabilities

| Capability            | Business value                                                                                           |
|-----------------------|----------------------------------------------------------------------------------------------------------|
| **Access control**    | All case data requires a logged-in user. Registration, login and API docs are public.                    |
| **Overload protection** | At most 5 concurrent database operations for case view and create. Extra requests get `503 Service Unavailable` right away instead of queuing, so the service stays responsive under spikes. |
| **Fast authentication** | User records are cached in Redis, so authenticating each request does not hit the database.            |
| **Audit trail**       | Methods marked `@AuditLog` log start, end, duration and errors. Only the case summary lookup (F5) uses it today. |
| **Consistent errors** | Errors are returned as `{ code, message, timestamp }` with codes `VALIDATION_ERROR`, `INVALID_ARGUMENT` and `ORDER_NOT_FOUND`. |
| **Observability**     | Health, metrics and Prometheus endpoints, with Grafana dashboards for API, JVM, DB connections and Redis in the repo root. |
| **API documentation** | Swagger UI at `/case-viewer/swagger-ui.html`.                                                            |

## 5. Gaps and known limitations (business view)

These are findings from reviewing the current code. They affect what the business can rely on.

| # | Area | Finding | Business impact |
|---|------|---------|-----------------|
| 1 | Activities | No API to add, update or list activities. `ActivityController` is fully commented out. | Case history can only be loaded directly into the database, so the timeline can't be maintained through the product. |
| 2 | Case lifecycle | No update, status change, close or delete endpoints. | Cases can't move from `OPEN` to `CLOSED` through the API. |
| 3 | Case creation | No input validation on `CaseRequest`. A missing title or status, or a duplicate `caseNumber`, reaches the database and likely returns a generic `500`. | Users get unclear errors, and the "unique case number" rule has no friendly message. |
| 4 | Case creation | No automatic `CASE_CREATED` activity, and the creating user isn't recorded. | Audit history for new cases is incomplete. |
| 5 | Authorization | Every logged-in user can see and create every case. Roles are stored but not checked. There are no admin, agent or read-only roles. | No separation of duties or data ownership. |
| 6 | Multi-tenancy | The `tenant-id` header is accepted but ignored. | Tenants' data is not isolated. |
| 7 | Search | No search by status, customer or date. The planned search endpoints exist only as comments. `list all` has no paging. | Users can't find work queues, and large datasets will be slow. |
| 8 | Inconsistent behaviour | F3 returns `404` for an unknown case but F5 returns `200` with an empty body. The not-found code is `ORDER_NOT_FOUND`, left over from the Order service template. | Confusing for API consumers. |
| 9 | Overload response | `503` returns plain text, not the standard error JSON. | Clients need special handling. |
| 10 | F7 endpoint | Hard-coded to `CASE-100002`. | Returns the wrong case for any other input. Remove it or fix it. |
| 11 | Data access | Three read paths (JPA, MyBatis, JDBC/stored procedure) for the same data. `sample-case-data.sql` uses PostgreSQL syntax (`ON CONFLICT`), while dev now points at Oracle. | Results can differ between endpoints, and the seed script won't run on Oracle. |
| 12 | Security hygiene | The dev profile commits DB and JWT secrets. The JWT filter prints tokens and user details to stdout (see ADR-0001). | Credentials can leak through the repo or logs. |
| 13 | Tests | The only test class was deleted. | No automated check protects the features above. |

## 6. Suggested next features (priority order)

1. **Activity management:** add an activity to a case and list activities (completes F3's value).
2. **Case update and status transitions:** enforce `OPEN → IN_PROGRESS → RESOLVED → CLOSED`, and log each change as an activity.
3. **Validation and duplicate handling** on case creation, with clear `400` or `409` errors.
4. **Search and paging:** by status, date range and (once modelled) customer or assignee.
5. **Roles and ownership:** agent, supervisor and read-only roles; case assignment.
6. **Tenant isolation** using the `tenant-id` header.
7. **Clean-up:** one data-access path, a `CASE_NOT_FOUND` error code, removal of the F7 prototype, and restored tests.
